# WorkBuddy 对齐清单（gdou-agent）

这份清单回答一个问题：**要做出一个 WorkBuddy，我们还缺什么。**

## 怎么用

1. 每行能独立开一个 spec，编号即 spec 名（如「H1 权限门」）。
2. 「WorkBuddy 机制」列写的是**内部实现**，不是界面描述。复刻时按这一列做。
3. 状态列只反映**代码里实际有的东西**，不反映文档里写过的计划。
4. 优先级在文末。

## 两条要交代清楚的来源

**第一，「WorkBuddy 机制」列是二手的。** 我们没有独立逆向过 WorkBuddy，这一列摘自
`kamibuddy-master/docs/workbuddy对齐清单.md`（212 条），而它的原始证据是：随包官方能力文档
64 篇 + `main/common.js` 的 **244 个 ProductFeature 特性开关枚举** + CLI bundle 工具名枚举 +
内置插件与技能目录 + 十一篇逆向笔记。**引用时必须标明是二手**，别把它当成我们自己的结论。

**第二，状态列是自评。** 判定口径：✅ = 代码里有且验证过；🟡 = 有但不完整；❌ = 没有；
⛔ = **有意不做**（并写明理由）。⛔ 和 ❌ 是两回事——⛔ 是决定，❌ 是缺口。

## 两根正交轴（照抄 kamibuddy §4.11 的方法论）

- **WorkBuddy 管「做什么」**：功能清单、交互形态、办公场景边界。它是规格书，因为「对齐」
  需要一个确定真源，否则账无从记起。
- **同类实现管「怎么做更好」**：codex / dsh / opencode / Trae / pi 提供底层机制与工程纪律。
- 判据是**「谁在本项目前提下更优」**，不是「谁新抄谁」。多数派只用来**发现缺口**
  （「五家全有、唯独我们没有」是缺口探测器），不作裁决依据。

本项目的前提：**单机桌面、零安装、BYOK、Windows 优先、pi 内核**。
每条都要按这五条重判一次。

## 一个必须先说清的架构分歧

**kamibuddy 用 npm 依赖引 pi，我们把 pi 源码 vendoring 进了仓库。**
它的理由是「不 fork。pi 迭代快，fork 即永久背 merge 债」（§2 技术选型），
而 vendoring 在效果上**就是一份 fork**——`vendor/pi` 是 701 个文件的副本，带 sha256 清单。

代价是真实的：pi 每次升级都要重跑 `vendor:pi` + `sync-paths`，且**我们自己改过的地方会被覆盖**。
收益是构建自持（不依赖隔壁 checkout）、离线可构建、内核行为完全可复现。

**这条分歧不急着改**，但它意味着 H/B 两节里「pi 自带」的项要打折看：
上游修了 bug，我们不会自动拿到。

## A. 壳层与进程架构

| 编号 | 能力 | WorkBuddy 机制（内部实现） | 我们 | 状态 |
| --- | --- | --- | --- | --- |
| A1 | 主进程职责收窄 | main 只做窗口/生命周期/safeStorage/托盘/更新，不解释业务 payload | `electron/main.ts`：窗口 + IPC + **内核直接跑在主进程内** | 🟡 内核在 main 里，职责没收窄 |
| A2 | 业务进程独立 | daemon 是独立子进程，入口带 `assertDaemonProcessRole()` 身份断言 | 无独立进程（内核与 UI 同进程） | ⛔ 单机桌面不必须；但见 A3 |
| A3 | 主↔业务 RPC | 自研 NDJSON stdio 帧协议 5 种帧，ready 握手 60s 超时 | 同进程调用，无 RPC | ⛔ 同上 |
| A4 | 业务面协议 | 会话走 ACP over streamable HTTP | 无 | ⛔ 单机不需要 |
| A5 | 会话保姆进程 | Sidecar 只做 spawn/pipe/reap；父死自愈 | 无（不 spawn CLI） | ⛔ 我们不 spawn 子进程 |
| A6 | Prewarm 进程池 | 冷启动 3.7s → ~1ms | 无 | ❌ 冷启动有体感差距 |
| A7 | 启动打点 | A–F 六段跨进程打点到同一 jsonl | 无 | ❌ |
| A8 | 崩溃治理 | respawn 退避 + 三级停止（RPC→SIGTERM→SIGKILL）+ stderr tail 上报 | 无（崩了就是崩了） | ❌ 桌面端可接受，但无诊断线索 |
| A9 | 单实例锁 | `app.requestSingleInstanceLock` | 已加：第二个实例退出，并把已有窗口恢复/聚焦 | ✅ |
| A10 | 托盘 / 多窗口 | 托盘菜单 + 窗口管理域 | 单窗口、无托盘 | ❌ |
| A11 | 自动更新 | 三平台 update-service | 无（手动分发） | ⛔ 内部分发不需要 |
| A12 | 应用菜单 | 自建 native 菜单（含快捷键与角色项） | 无（Electron 默认，且无边框窗口下不可见） | ❌ |
| A13 | 后台终端持有与回收 | daemon 侧集中持有后台终端 + 宽限期回收 | 无（没有后台执行） | ❌ 随 C3 |

**A 节小结**：WorkBuddy 的五层（Renderer→Main→Daemon→Sidecar→CLI）里，
我们**只有两层**。这不全是缺口——A2/A3/A4/A5 是**有意不做**（单机桌面、不 spawn CLI、
不接 IDE）。真正的缺口是 A9 单实例锁（便宜，会咬人）和 A12 应用菜单（无边框窗口下，
文件/视图/帮助 目前是自绘的，功能面比原生菜单窄）。

**A1 是个真问题**：内核跑在 main 进程里，意味着一次 LLM 调用的卡顿会直接卡住窗口。
kamibuddy 用 `utilityProcess` 隔开。要不要跟，取决于我们什么时候会做「长时间后台任务」
——在那之前不急着拆。

## B. Agent 内核

| 编号 | 能力 | WorkBuddy 机制（内部实现） | 我们 | 状态 |
| --- | --- | --- | --- | --- |
| B1 | Agent 主循环 | 不自研，bundle `@openai/agents` 的 Runner | 不自研，用 pi 的 `AgentSession` | ✅ |
| B2 | 最大轮次 | `DEFAULT_MAX_TURNS=500`，可环境变量覆盖 | pi 自身控制 | 🟡 未暴露为配置 |
| B3 | 流式事件 | delta / tool_calls / reasoning 三类累积，多路复用给 TUI/ACP/stream-json | pi 事件流 → `kernel/events.ts` **归一化词表** → 各前端 | ✅ 归一化层是我们的加分项 |
| B4 | 中断与插队 | abortController + 排队消息可 ↑ 拉回编辑 | abort（CLI/TUI/GUI 都有） | 🟡 无插队、无排队 |
| B5 | fallback 模型 | overloaded 先重试主模型再切 fallback | `kernel/fallback.ts`：**在产出任何内容之前**失败才切；先重试同一模型，重试耗尽才换；切换发 `notice`；`AgentSession.fallback` 暴露给前端 | ✅ **已完成（2026-09-23）** |
| B6 | 推理强度 | reasoningEffort + 设置项 + alwaysThinkingEnabled | pi `thinkingLevel`（逐会话持久化、resume 还原）；专家可声明 `thinkingLevel` | ✅ v1：无 per-model 档位 |
| B7 | 场景模型变体 | `relatedModels.{lite,reasoning}`，lite 用于子代理/压缩/评估 | 模式文件的 `model:` 字段——**最低优先级建议**（选项 > 设置 > 模式），未知 spec 在会话启动时报错并点名模式与文件 | 🟡 **部分完成（2026-09-23）**：有了「按场景选模型」的机制，但**还没有任何调用点真的用它**——压缩、评估、子代理都还没有，所以它现在是给用户用的，不是内部省钱用的 |
| B8 | 模型目录 | 内置 product.json（云下发）+ 用户/项目 models.json + 白名单 | pi 内置 provider 目录；`--list-providers` | 🟡 无用户级自定义模型 |
| B9 | 结构化输出 | `StructuredOutput` 工具，按 JSON Schema 返回 | 无 | ❌ |
| B10 | 死循环检测 | 同参重复 N 次发喝止消息 | `kernel/loop-guard.ts`：同工具同参数**连续**重复超过 N 次（默认 3）拦下，理由作为 error 工具结果回给模型；拦在**权限门之后**；`loopRepeatLimit: 0` 关掉 | ✅ **已完成（2026-09-23）** |
| B11 | 重试策略 | HTTP 层 maxRetries + 指数退避 + 尊重 Retry-After | pi 自带 | ✅ |
| B12 | IDE 内联补全 | Completions/NES 全家桶 14 个开关 | 无 | ⛔ 桌面对话形态无此面 |

**B 节小结**：内核层我们**不需要做什么**——B1/B3/B11 已经是 pi 给的，B6 做得比清单还细。
三个**成本与稳定性**缺口已补齐（2026-09-23）：**B10 死循环检测**、**B5 fallback 模型**、
**B7 按场景选模型**的机制。

但 B7 要如实降级成 🟡：**机制在，调用点不在**。WorkBuddy 的 `lite` 模型是给
「子代理 / 压缩 / 评估」这类内部环节用的——那些环节现在一个都还没有，所以
`model:` 字段目前是**给用户用的**（一个只在某个模型上表现好的模式可以自己声明），
不是**给内部省钱用的**。等子代理落地的那个下午，它才真正开始省钱。
把它说成 ✅ 会掩盖这个差别。

## D. 办公内置插件（产品价值核心）

kamibuddy 的判断值得引用：**「WorkBuddy 投入最大的一块，而且完全不依赖腾讯云
——这是最值得抄的部分。」** 但「值得抄」不等于「我们能抄」：

| 编号 | 能力 | WorkBuddy 机制（内部实现） | 我们 | 状态 |
| --- | --- | --- | --- | --- |
| D1 | 本地 docx 生成 | `tencent-docx`：根 SKILL 编排器 + 3 agents + 8 skills + 9 个文体专家 + 20 多个模块的 Python html→docx 转换器 | 无 | ❌ **需要 Python 运行时，成本最高的一项** |
| D2 | 表格智能体 | `sheetagent`：内嵌 MCP（stdio）+ 10 篇 sheet-references | 无 | ❌ |
| D3 | 幻灯片 | `tencent-pptx` 插件 | 无 | ❌ |
| D4 | 腾讯文档集成 | 按身份路由 C 端/SaaS | 无 | ⛔ 依赖腾讯生态 |
| D5 | 支付插件 | `weixinpay` | 无 | ⛔ |
| D6 | 本地 Office 编辑 | `tencent-local-office-edit` + editor_sdk 本地引擎 | 无 | ⛔ **一个团队的量级** |
| D7 | 知识库集成 | 乐享 / ima 知识库接入对话 | 无 | ⛔ 依赖腾讯知识库服务 |

**D 节小结**：这一节**不要现在碰**。D1 是「产品价值核心」没错，但它的成本不在代码，
在**随包 Python 运行时 + 转换引擎的持续维护**。kamibuddy 能搬是因为它有现成的
`tencent-docx` 引擎可搬（29 模块），我们从零写一个 html→docx 转换器是**几周**的活，
而且注定比 LibreOffice / Pandoc 差。

**如果要走「用现成的」这条路**，正确的形态不是自己写引擎，而是：
装一个 `docx` 的 npm 库（如 `docx`）做**基础生成**，把复杂排版交给用户已有的 Office。
这条要单独拍板。

**E 节小结 —— E5 值得单独说。**

我们在专家机制上**已经走通了对齐**：`SessionRecipe { mode, expert? }` 是模式 × 专家的
正交组合，专家是 markdown 文件（frontmatter + 正文方法论），三级加载，
**且专家只能收窄工具集不能扩大**。最后这条是**安全属性**：专家是用户自己写的文件，
如果它能加工具，「装个专家」就等于「装个后门」。

kamibuddy 的 E5 里有一项我们没有、但值得抄：**`<current-expert>` 每轮钉子**。
我们只在构造时注入一次人格段，它每轮重钉一次。原因是长对话里人格会漂移。

**E1 是这一节唯一真正新的机制，也是「渐进式披露」的全部价值所在**：
会话开始时上下文里只有每个 skill 的**名字 + 一句话描述**，任务匹配后模型才调
`load_skill` 把正文读进来。不这么做的话，几十个 skill 全文塞进系统提示就是几十万 token
——正好把上下文裁剪省下来的预算又花回去。

**E1 已于 2026-09-23 落地**：`skills/`（目录 + `SKILL.md` + `references/`）三级加载，
提示里只注入目录，`load_skill` 工具按需读正文。内置两个技能证明机制，实现见
`FEATURES.md 2.36`。E2–E9（内置技能包、自维护、安装、安全扫描、意图召回）都还空着——
它们要么是「内容」不是「机制」（E2 内置包），要么排在第三梯队之后（E4 安装、E8 安全扫描）。

**F 节小结**：**F1 曾是我们和 kamibuddy 之间最根本的一处形态差异——现已弥合（2026-09-23）。**

模式提示词原来写死在 `src/profiles/general.ts` / `coding.ts` 的模板字符串里；
它们放在 `resources/modes/*.md`。差别不是「谁优雅」，是**加一个模式要不要改代码**。

现在模式是 markdown（`~/.gdou-agent/modes/` 与 `<cwd>/.gdou-agent/modes/`，
三级加载），**加一个模式 = 加一个文件**。

**但有一处我们做不到、也不该假装做到**：`resources/` 不参与构建
（`scripts/build.mjs` 只拷 `renderer/`），所以内置模式是 `builtin.ts` 里的内联字符串，
不是随包的文件。用户模式是真文件；内置的只是走同一个解析器。

另外**工具集仍然是代码**：frontmatter 里写工具**名**，由
`src/profiles/tool-catalog.ts` 解析成工具。所以「加一个模式 = 零行代码」
只对**组合已有工具**的模式成立；需要一个新工具的模式仍然要写代码。
**工具就是代码，数据文件不能凭空提供代码**——把这条说清楚比把承诺说大有用。

而且 **F2 的「双面文件」我们已经为专家实现了**（`frontmatter.ts` 就是那个解析器）——
把它复用到模式上，是**纯机械改动**，不需要新机制。这是「能力即数据」最便宜的一步。

F13（地域约定）和 F8（风格系统）是**几乎零成本**的两项，抄过来就能用。

## H. 权限与安全

**这一节是我们的最大缺口，而且性质和其他节不同：别的节是「还没做」，这节是「现在就有风险」。**

起点是一个事实：**pi 没有任何路径约束。** kamibuddy 在 §4.57 里查证过——
`utils/paths.ts` 的 `resolvePath` 对绝对路径直接放行，工具目录里搜不到越界检查。
即：**模型给出绝对路径就能写到硬盘任意位置，包括覆盖 `auth.json` 里的 API Key。**
pi 的 README 自己也写着 "does not include a built-in permission system"。

我们 vendoring 了同一份源码，所以**继承同一个前提**。而我们 `coding` 模式暴露了 `bash`。

### 如果要抄，抄哪几条（按性价比排序）

kamibuddy 的判定链设计里有几条**推理**比代码更值钱，直接可搬：

1. **判定主轴是「路径归属」而不是「工具种类」。** 按工具种类判会漏——同一个 `write`
   写工作区内和写 `~/.ssh` 是两件事。
2. **凭据目录禁读也禁写，任何档位不能越过。** 它的理由是「泄露即账号级损失，
   不该由一次弹窗决定」。而且它**改过一次**：原先只禁写、允许读，理由是「读到也带不走」；
   **`web_fetch` 落地后这个前提消失了**——提示注入可以「读 auth.json → 抓一个 URL 带上内容」。
   **这条推理对我们直接适用**：一旦我们做 C4 联网，凭据必须同时禁读。
3. **shell 在任何档位都拦，包括「允许完全访问」。** fail-closed 到有危险命令分类器为止。
   理由是一句命令就能绕开所有路径保护（`type ~\.ssh\id_rsa`）。
4. **审批策略 `never` 把「询问」转成「拒绝」。** 无人值守时「不问」必须等于「不做」，
   不是「随便做」。
5. **高风险询问不支持「本次会话记住」**，且记住按**工具 + 目标目录**记、只在内存里。
   批准「写桌面」不该顺带批准「写 `C:\Windows`」。
6. **项目信任是一道独立闸。** `.pi/extensions` 是 TS 模块，**加载即以本进程权限执行任意代码**，
   权限门拦不到（那不是工具调用）。打开陌生目录必须先问。

**H14 是单点性价比最高的一项**：不依赖 OS 沙箱、不依赖 UI、纯字符串判定，
但能挡住「一条命令绕开所有路径保护」这个最致命的洞。

| 项 | 状态 | 落地位置 |

**第零梯队全部完成。**

**实现上有三处值得记下来的判断**：

1. **按参数形状分类，不按工具名分类。** 第一版用一个工具名白名单，未登记的走 `ask`——
   而没有审批通道时 `ask` 等于拒绝。后果是**任何模式新增的工具都被直接拒掉**
   （TUI 自检里一个只收 `count` 的探针工具就被拒了），agent 自己的工具也会。
   正确的推理是：**这道闸保护的面是「路径」和「命令」，两者都不带的调用没有面可保护**，
   拒绝它保护不了任何东西，只是把功能弄坏。改成按参数形状判定后，
   未识别但带 `path` 的工具**仍然**会被检查（并按写入处理）。

2. **`ask` 无人应答时必须等于拒绝。** 失败开放的闸不是闸。

3. **判定链的有序性是可断言的性质**，不是文档承诺：`danger-full-access` 档位下读
   `~/.ssh/id_rsa` 仍然被拒，因为档位在 stage 4 才被查询，而凭据在 stage 1 已经返回。
   这一条在 smoke 里是逐个档位断言的。

**尚未解决**：命令检查器是**黑名单**，不是沙箱——它提高门槛，不建立边界。
真正的解法是 OS 级（受限令牌 + Job Object，即 H10），那是另一个量级的工程。

## 探索项 · JEV 前置模型（放最后，不着急）

> **状态：仅规划，未排期。** 记在这里是为了不让这条想法丢，不是现在要做。

**想法**：探索用 **JEV**（一个更小、更快的判定模型）作为**前置筛选器**，
在把请求发给大模型之前，先由 JEV 判断「这个问题/这一步的置信度」。

- **高置信度**：JEV 自己就能答，或判断「这一步不需要大模型」，直接返回，
  省掉一次大模型调用。
- **低置信度**：JEV 判不了 / 该上大模型，才把请求交给主模型。

**目标**：减少 token 开销。很多简单、重复、确定性的子问题（格式转换、
固定问答、已知事实复述）不需要每次都烧大模型的 token。

**为什么放最后**：
- 它依赖 **B7 场景模型变体**（JEV 本质上是一个 `lite` 模型，挂在同一个
  「按场景选模型」的机制上）——而 B7 的调用点（子代理 / 压缩 / 评估）还没做。
- 它需要**置信度判定**这个前置环节，和子代理、评估同属「内部省钱」那一层，
  等那一层落地了才有真正的挂点。
- 它引入**双模型一致性风险**：JEV 判「高置信度」但判错，代价是用户拿到错误答案
  而不是「省了 token」——这个边界要先想清楚（比如只对**可验证、低风险**的子问题放行）。

**落地时的形态猜测**（先记，做的时候再推翻）：
1. JEV 是一个独立 provider / 模型，复用现有 `resolveDefault` 的解析路径。
2. 在「发请求前」插一个判定钩子：`kernel` 层加一个 `preflight` 阶段，
   或复用 B7 的「场景模型」挂点。
3. 只在**确定性高、后果可逆、可验证**的任务上放行 JEV 直答，其余一律回大模型。
4. 需要一个**可观测的判据**：JEV 拦截了多少次、省了多少 token、判错了几次——
   否则「省钱」只是猜测。

**这条和 B7 的关系**：JEV 前置 = B7 的 `lite` 模型在「请求前判定」这个新场景上的
第一次真正使用。等 B7 有第一个调用点（子代理）之后，这条自然就有了参照系。

## 探索项 · 用量统计（未来方向）

> **状态：仅规划，未排期。** 记在这里是为了方向不丢，不是现在要做。

**想法**：给用户一个「花了多少 token / 多少钱」的可见视图。对照清单里的 **L16
用量与成本**（WorkBuddy 有 `/cost`、`/context`、`/stats`、`/insights` 四个面板，
我们现在只有检查器里一条「模型可见 N/M 条」）。

**为什么值得做**：BYOK 模式下，钱是从用户自己的 key 里扣的——「这一轮对话花了
多少」不是猎奇，是**账**。没有它，用户对成本是瞎的，而且没法知道「这个模式 /
这个模型是不是太烧钱」。

**它和 JEV 前置、B7 场景模型的关系**：三者是同一个命题的三个面——**省钱**。
用量统计是「看见」、B7 是「换便宜的模型」、JEV 是「根本不叫大模型」。顺序上
用量统计应该**最先**，因为先有账，才知道省没省下来、值不值得省。

**落地时的形态猜测**（先记，做的时候再推翻）：
1. 数据源：pi 每次请求返回的 `usage`（token 数）。现在 `kernel/events.ts` 归一化时
   大概率没把它带出来，需要先确认 pi 的 usage 在哪个事件里。
2. 聚合点：`AgentSession` 或 `kernel/events.ts` 里累积 per-session 的 token 计数，
   存进会话记录（`sessions/*.json` 的摘要行已经有 messageCount，可再加 token 字段）。
3. 展示：检查器里一行「本次会话 N tokens ≈ ¥M」起步，够用；完整的 `/cost` 面板
   是后面的事。
4. 计费：token → 钱需要一个价格表（各 provider 各模型的单价），这是**外部数据**，
   要么内置一份简表、要么让用户填单价——先内置常见 provider 的粗略价，标注是估算。

**放这里而不是排进梯队的原因**：它不是「卡住下一步」的依赖项，是一个持续有用的
观察面。等观测（N6/N7/N9）和子代理做完、有真实使用量了，再回来做它才有意义——
否则统计的是「没人用的数字」。
